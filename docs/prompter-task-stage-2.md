# Завдання для промптера — етап 2: хмара, акаунти, гостьовий доступ

**Джерела істини:** [stage-2.md](stage-2.md) — дельта етапу 2 · [spec.md](spec.md) + [interactions.md](interactions.md) — база, чинна для всього неперевизначеного · [style-guide.md](style-guide.md) — стиль · [tech-stack.md](tech-stack.md) — архітектура.

**Що на виході:** застосунок із акаунтами, хмарним сховищем і публічними посиланнями на списки. Етап 1 уже реалізований — це **надбудова над ним**, не переписування.

---

## 1. Рамка

**Стек:** Next.js (App Router) + React + TypeScript · **MongoDB** (Atlas M0) · **Cloudinary** для картинок · **Auth.js (NextAuth)** з Credentials provider.

**Ключове архітектурне:** на етапі 1 весь доступ до даних іде через інтерфейси `WishRepository` / `ProfileRepository` з реалізацією на IndexedDB. Етап 2 додає **другу реалізацію** — на MongoDB через Server Actions. Компоненти, що споживають репозиторій, правити не потрібно. Якщо в коді етапу 1 цього шару немає — його треба зробити **до** підключення бази, інакше зміни розповзуться по всіх компонентах.

**Тепер серверні компоненти нарешті потрібні.** На етапі 1 усе було клієнтським через IndexedDB. Тепер:
- гостьовий екран `/w/{token}` — **повністю серверний** (швидко, працює без JS, коректні OG-теги);
- «Мої бажання» — початкові дані з сервера, інтерактив клієнтський;
- мутації — Server Actions, не клієнтські запити до API.

## 2. Модель даних (MongoDB)

```
User {
  _id: ObjectId
  email: string            // unique, нижній регістр
  passwordHash: string     // bcrypt, cost 12
  name: string             // 3–15 символів
  shareToken: string       // unique, випадковий ~10 символів
  createdAt: Date
}

Wish {
  _id: ObjectId
  userId: ObjectId         // індекс
  title: string            // до 60
  emoji: string            // дефолт "🎁"
  imageUrl: string | null
  imagePublicId: string | null   // без нього файл не видалити з Cloudinary
  price: number | null
  currency: "UAH" | "PLN" | "USD" | "EUR"
  url: string | null
  isDone: boolean
  createdAt: Date
}
```

Індекси: `User.email` unique · `User.shareToken` unique · `Wish.userId`.

## 3. Автентифікація

**Імейл + пароль.** Пароль мінімум 8 символів, bcrypt cost 12, ніде не логується у відкритому вигляді. Імейл — `trim` + нижній регістр, унікальний. Сесія — JWT у httpOnly-cookie.

### `/register` — замінює Init-екран етапу 1

Поля: **імʼя** (3–15, валідація точно як на Init) · **імейл** · **пароль** (мін. 8). Кнопка «Створити акаунт» неактивна, поки всі три не валідні.

Після успіху: створити `User` з випадковим `shareToken` → міграція локальних даних або 3 дефолтні картки (розділ 6) → «Мої бажання».

Помилки інлайн, Ember: «Такий імейл уже зареєстрований» · «Пароль мінімум 8 символів» · «Схоже, це не імейл».

### `/login`

Імейл, пароль, кнопка «Увійти», посилання «Немає акаунта? Створити».

**Помилка входу завжди одна:** «Невірний імейл або пароль» — не уточнювати, що саме не збіглося (інакше форма стає інструментом перевірки, чи зареєстрований імейл).

**Посилання «Забули пароль?» не додавати** — скидання не реалізоване (немає сервісу розсилки). Кнопка, що нікуди не веде, гірша за її відсутність.

### Вихід

Меню профілю на «Мої бажання» (клік по імені) отримує два пункти: «Змінити імʼя» і «Вийти».

### Захист маршрутів

`/`, `/add`, `/share` — тільки для автентифікованих, інакше редирект на `/login`. `/w/{token}`, `/login`, `/register` — публічні.

## 4. Ліміт 30 бажань

Рахуються **всі** бажання — активні й здійснені.

- **Серверний хардлок обовʼязковий:** Server Action відхиляє створення 31-го. Клієнтська перевірка — зручність, не гарантія.
- `< 25 бажань` → нічого не показуємо.
- `≥ 25` → у хедері поруч із лічильником муте-текст «28 / 30».
- `= 30` → кнопка «Додати» неактивна + підпис «Ліміт 30 бажань. Видали щось, щоб додати нове». Якщо форма якось відкрита — кнопка збереження неактивна з тим самим текстом.
- Видалення одразу знімає блокування.

## 5. Поділитися і гостьовий перегляд

### 5.1. Екран «Поділитися» (свій)

До наявного банера, карток і «Зберегти як картинку» додається:

- **Поле з посиланням** `https://…/w/8f3k2p9x` — read-only інпут + кнопка «Копіювати» (2с «Скопійовано ✓»).
- Кнопка «Поділитися» тепер передає у Web Share API **і текст, і `url`** — щоб месенджери зробили клікабельне прев'ю. Фолбек на desktop копіює текст разом із посиланням.

### 5.2. `/w/{token}` — гостьовий екран, серверний рендер

**Показує:**
- Банер Amber `#f59e0b`, текст `#0a0a0a`: «Список бажань {імʼя}» + лічильник.
- Картки: емодзі/картинка, назва, ціна, **посилання «Подивитися →»** (нова вкладка, `rel="noopener noreferrer"`).
- Здійснені бажання **не показуються** і не рахуються.
- Жодних кнопок дії. Картки некликабельні, крім посилання.
- Внизу — CTA-банер «Створити свій список бажань» → `/register`, у стилі Neutral Card. Без модалок, без таймерів, без затемнення.

**Окремої кнопки «Переглянути як гість» немає** — список відкривається одразу, без шлюзу. Це і є «простіший доступ».

**Стани:**

| Ситуація | Що показуємо |
|---|---|
| Токен не існує | «Такого списку не існує» + кнопка «На головну» |
| Порожньо / усе здійснене | Банер + «Тут поки порожньо» + CTA реєстрації |
| Гість залогінений | Той самий read-only; CTA внизу → «Мій список» на `/` |
| Відкрив власне посилання | Той самий вигляд + підказка «Так твій список бачать друзі» |

**OG-теги** для прев'ю в месенджерах: заголовок «Список бажань {імʼя}», опис із кількістю бажань.

## 6. Міграція локальних даних (одноразово, при першому вході)

Клієнт перевіряє IndexedDB після успішної автентифікації:

1. **Є локальні бажання** → заливаються в акаунт: Blob-картинки вивантажуються в Cloudinary, записи створюються з новим `userId`. **Дефолтні 3 картки не створюються.** Після успіху IndexedDB очищається.
2. **Локальних немає** → створюються 3 дефолтні: 📚 Книжка про дизайн ₴450 · ✈️ Вихідні у Львові ₴3 000 · 🎧 Навушники ₴2 200 (здійснене). Редагуються й видаляються як звичайні, рахуються в ліміті.
3. **Локальних більше 30** → переносяться перші 30 за `createdAt`, решта відкидається + повідомлення «Перенесено 30 з N бажань — це максимум для акаунта».

Під час процесу — індикатор «Переносимо твої бажання…». Міграція **ідемпотентна**: якщо впала на середині, повторний вхід доливає те, чого бракує, а не дублює вже перенесене.

## 7. Cloudinary

- Завантаження **через Server Action із підписаним запитом**. Unsigned preset не використовувати — з ним будь-хто зможе заливати файли у ваш акаунт.
- Обмеження ті самі: 5 МБ, JPEG/PNG/WebP/GIF, клієнтське стиснення до ~1200px перед відправкою.
- Зберігати `secure_url` **і `public_id`**.
- Видалення бажання → видалення файлу з Cloudinary. Якщо видалення файлу впало — бажання все одно видаляється, помилка логується.
- Секрети — тільки в змінних оточення, ніколи в клієнтському бандлі.

---

## 7.1. Змінні оточення

Значення **не потрапляють ні в репозиторій, ні в документацію** — тільки імена. Заводить їх той, хто налаштовує середовище: локально в `.env.local`, на проді — у налаштуваннях хостингу.

```
MONGODB_URI=              # секрет: рядок підключення до Atlas
CLOUDINARY_URL=           # секрет: cloudinary://<api_key>:<api_secret>@<cloud_name>
AUTH_SECRET=              # не секрет ззовні — генерується: openssl rand -base64 32
AUTH_URL=                 # не секрет: http://localhost:3000 локально, https://домен у проді
```

**Cloudinary конфігурується однією змінною.** `CLOUDINARY_URL` містить `cloud_name`, `api_key` і `api_secret` разом; Node-SDK читає її з оточення сам — `cloudinary.config()` без аргументів. Окремі `CLOUDINARY_CLOUD_NAME` / `_API_KEY` / `_API_SECRET` заводити не потрібно, і не варто: два джерела істини для одного доступу неминуче розʼїжджаються.

**Жодна змінна не має префікса `NEXT_PUBLIC_`.** Цей префікс вшиває значення в клієнтський бандл. `CLOUDINARY_URL` там означав би, що будь-хто з DevTools дістає ваш `api_secret` і заливає файли у ваш акаунт.

Клієнту `cloud_name` не потрібен: завантаження йде через Server Action, а в базі лежить готовий `secure_url` — картинки віддаються за прямим посиланням, без побудови URL на клієнті.

До репозиторію додати:

- `.env.example` — ті самі ключі з порожніми значеннями, як шаблон.
- `.env.local` і `.env*.local` у `.gitignore` — перевірити до першого коміту, а не після.

## 8. Що НЕ чіпати

Уся продуктова логіка етапу 1 лишається як є:

- «✓» з тьмянінням і переміщенням картки вниз, оборотність.
- Інлайн-видалення на картці (не модалка), одночасно тільки одне.
- Фільтр «Усі / Активні / Здійснені», скидання на «Усі» при вході.
- Три різні порожні стани.
- Підсвічування нової картки при поверненні з «Додати».
- Форма «Додати»: поля, порядок, валідація, взаємовиключність емодзі й картинки, скасування з підтвердженням.
- Відмінювання лічильника, форматування ціни `₴3 000`.
- Дизайн-система: радіуси 18/24, Ember тільки деструктив, Amber тільки банери «Поділитися» і `/w/`.
- «Зберегти як картинку».
- Клавіатура, мобільна поведінка, `prefers-reduced-motion`.

## 9. Чек-лист приймання

- [ ] Реєстрація створює акаунт; повторний імейл дає зрозумілу помилку
- [ ] Пароль зберігається тільки хешем; у логах і відповідях API його немає
- [ ] Вхід працює; хибні дані дають однакову помилку без уточнень
- [ ] Неавтентифікований користувач із `/`, `/add`, `/share` летить на `/login`
- [ ] Новий акаунт без локальних даних отримує рівно 3 дефолтні картки
- [ ] Локальні бажання з етапу 1 переносяться при першому вході, IndexedDB очищається
- [ ] Повторна міграція нічого не дублює
- [ ] На 30 бажаннях додавання блокується **і на клієнті, і на сервері**
- [ ] Від 25 бажань зʼявляється «N / 30»
- [ ] `.env.local` у `.gitignore`; у репозиторії лежить `.env.example` без значень
- [ ] Жодного секрета під префіксом `NEXT_PUBLIC_`; у зібраному бандлі їх не видно
- [ ] Картинка вантажиться в Cloudinary через сервер; `public_id` збережений
- [ ] Видалення бажання видаляє файл із Cloudinary
- [ ] `/w/{token}` відкривається без входу й **працює з вимкненим JS**
- [ ] Гість бачить назви, ціни й посилання; здійснених бажань не бачить
- [ ] Гість не може нічого змінити — ні через UI, ні прямим викликом Server Action
- [ ] Неіснуючий токен дає «Такого списку не існує», а не 500
- [ ] Копіювання посилання працює; Web Share передає текст і URL
- [ ] Уся поведінка етапу 1 не зламалась

## 10. Дві речі, які варто знати

**1. Відновлення пароля не існує.** У стеку немає сервісу розсилки, тож забутий пароль = втрачений акаунт разом зі списком. Для воркшопу нормально; для реального запуску потрібен або сервіс листів (Resend / Postmark, безкоштовні тарифи є), або вхід через Google як другий шлях. Деталі — [stage-2.md 3.4](stage-2.md).

**2. Гість бачить посилання на товари — це відхилення від етапу 1.** У [spec.md 3.3](spec.md) екран «Поділитися» показував лише емодзі, назви й ціни. Для гостьового перегляду посилання додано навмисно: гість дивиться список, щоб щось купити, і без URL мусить шукати товар сам. Якщо це небажано — приберіть пункт із 5.2.
