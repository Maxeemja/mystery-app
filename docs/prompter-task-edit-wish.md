# Завдання для промптера — редагування бажання

**Тип:** окремий інкремент поверх наявного застосунку. Не переписування.
**Джерела істини:** [interactions.md 3-bis](interactions.md) — повна поведінка · [spec.md 3.3-bis](spec.md) — продуктовий опис · [stage-2.md 7-bis](stage-2.md) — право власності · [style-guide.md](style-guide.md) — стиль.

---

## 1. Що треба зробити

Дати власнику списку змінювати вже створене бажання. До цього єдиним способом виправити помилку було видалити картку й створити заново.

**Три частини роботи:**

1. Третя кнопка на картці — олівець.
2. Маршрут `/edit/{id}` — та сама форма, що `/add`, у режимі редагування.
3. Серверна перевірка права власності на **всіх** мутаціях бажання, не тільки на редагуванні.

**Доступ:** лише власник, лише зі своїх екранів. На гостьовому `/w/{token}` редагування немає ні як кнопки, ні як маршруту.

---

## 2. Кнопка на картці

Картка зараз має «✓» і кошик. Додається олівець — між ними за змістом, але не за розташуванням.

- **«✓»** лишається окремо, як головна дія.
- **Олівець і кошик** — групою в протилежному куті, олівець перед кошиком. Деструктивна дія остання, щоб не влучити випадково.
- Видимість — за наявним правилом: desktop — по hover картки (fade 150мс), mobile — завжди.
- Іконка — той самий тонкий геометричний стиль, що решта. Колір `#0a0a0a` / `#737373` у стані спокою. **Не Ember** — редагування не деструктивне.
- На mobile тап-таргети не менші за 44px. Перевірити, що три кнопки вміщаються, не стискаючи назву бажання.

---

## 3. Маршрут `/edit/{id}`

### 3.1. Перевикористання форми — обовʼязкове

Береться **той самий компонент**, що на `/add`. Не робити другу форму: поля, порядок, валідація, взаємовиключність емодзі й картинки, форматування ціни пробілами, автододавання `https://`, ліміт 60 символів на назву — усе це вже реалізоване й має працювати ідентично.

Режим передається пропом. Дублювання форми означає, що будь-яка майбутня правка робиться двічі й одного разу забудеться.

### 3.2. Відмінності від режиму створення

| | `/add` | `/edit/{id}` |
|---|---|---|
| Заголовок | «Додати бажання» | «Редагувати бажання» |
| Кнопка | «Додати бажання» | «Зберегти зміни» |
| Початковий стан полів | порожні | заповнені поточними значеннями |
| Автофокус | «Що це?», порожнє | «Що це?», курсор у кінці тексту |
| Кнопка активна коли | назва не порожня | назва не порожня **І** хоч одне поле змінене |
| Скасування питає коли | хоч одне поле заповнене | хоч одне поле **змінене** |

**Dirty-check — не педантизм.** Форма памʼятає початковий стан і порівнює з поточним. Активна кнопка «Зберегти», яка нічого не зберігає, читається як зламана; а підтвердження «Скасувати зміни?» при відсутності змін — як зайве тертя.

### 3.3. Що не редагується

- **`isDone`** — це кнопка «✓» на картці, у формі її немає.
- **`createdAt`** — не змінюється при збереженні. Від цього залежить позиція картки (див. 3.4).

### 3.4. Збереження

1. Запис оновлюється, `createdAt` лишається як був.
2. Перехід на «Мої бажання».
3. Картка підсвічується **на своєму місці** — той самий тон, що для нової картки (`#ffffff → #f5f5f5`, ~900мс).
4. **Позиція в списку не змінюється.** Сортування за `createdAt`, він не чіпався. Виправлення одруківки в назві не має відкидати картку нагору списку — це виглядало б як баг.
5. Здійснене бажання лишається здійсненим і лишається у своїй групі.

## 4. Картинки при редагуванні

Найризикованіша частина — тут легко залишити осиротілі файли в Cloudinary або, навпаки, видалити потрібний.

| Дія | Поведінка |
|---|---|
| Була картинка → завантажили нову | Стара замінюється. Старий файл видаляється **після успішного збереження**, не раніше |
| Була картинка → натиснули «×» | Картинка прибирається, повертається вибір емодзі. Якщо емодзі не вибране — `🎁` |
| Було емодзі → завантажили картинку | Емодзі скидається, як і при створенні |
| **Скасували редагування** | **Жоден файл не видаляється** |

Правило одне: сховище чіпається тільки при успішному збереженні. Видалення старого файлу до збереження означає, що збій запису лишить бажання без картинки.

---

## 5. Право власності — серверне

Це не деталь реалізації, а суть вимоги «редагувати можна, якщо ти власник».

- Кожна мутація бажання — `create`, `update`, `toggleDone`, `delete` — перевіряє на сервері, що `wish.userId === session.user.id`. Перевірка в **Server Action**, не в компоненті.
- **Приховати кнопку в UI недостатньо.** Server Actions викликаються прямим HTTP-запитом; зловмиснику ваша кнопка не потрібна.
- **Чуже і неіснуюче бажання дають однаковий 404.** Якщо чуже віддає 403, а неіснуюче 404, різниця відповідей стає способом перебирати, які `id` існують у базі.
- Перевірка живе в **одному** місці — хелпер на кшталт `requireOwnedWish(id, session)`, який або повертає документ, або кидає 404. Умова, продубльована в кожному екшені, рано чи пізно десь забудеться.

Це стосується не тільки нового редагування — наявні `toggleDone` і `delete` теж мають пройти через той самий хелпер, якщо ще не проходять.

## 6. Крайні випадки

| Ситуація | Поведінка |
|---|---|
| Бажання видалене з іншої вкладки, поки форма відкрита | При збереженні — «Це бажання вже видалене», перехід на список |
| `/edit/{id}` чужого бажання | 404, без натяку на існування запису |
| `/edit/{id}` неіснуючого `id` | Той самий 404 |
| `/edit/{id}` без автентифікації | Редирект на `/login` |

---

## 7. Що не має зламатись

- Поведінка `/add` — жодних змін. Перевірити після рефакторингу форми під два режими.
- «✓» з тьмянінням і переміщенням картки, оборотність.
- Інлайн-видалення на картці, одночасно тільки одне активне.
- Фільтр, три порожні стани, підсвічування нової картки.
- Ліміт 30 бажань — редагування його не торкається (нових записів не створює).
- Дизайн-система: радіуси 18/24, Ember тільки деструктив, тіні тільки на картках.

---

## 8. Чек-лист приймання

- [ ] Олівець зʼявляється на картці за тими самими правилами, що «✓» і кошик
- [ ] На mobile три кнопки вміщаються, тап-таргети ≥44px, назва не стискається
- [ ] `/edit/{id}` відкриває форму із заповненими поточними значеннями
- [ ] «Зберегти зміни» неактивна, поки жодне поле не змінене
- [ ] «Зберегти зміни» неактивна при порожній назві
- [ ] Скасування без змін виходить одразу; зі змінами — питає підтвердження
- [ ] Після збереження картка підсвічується **на своєму місці**
- [ ] Позиція картки в списку не змінюється після редагування назви
- [ ] Здійснене бажання після редагування лишається здійсненим і в своїй групі
- [ ] Заміна картинки видаляє стару з Cloudinary після збереження
- [ ] Скасування редагування не видаляє жодного файлу
- [ ] Видалення картинки через «×» повертає емодзі (дефолт `🎁`)
- [ ] `/edit/{id}` чужого бажання → 404, ідентичний 404 для неіснуючого
- [ ] Прямий виклик Server Action на чуже бажання відхиляється на сервері
- [ ] `toggleDone` і `delete` теж перевіряють власника на сервері
- [ ] На `/w/{token}` немає ні кнопки редагування, ні доступу до маршруту
- [ ] `/add` працює точно як раніше
