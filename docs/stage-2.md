# Wishlist — етап 2: хмара, акаунти, гостьовий доступ

**Статус:** специфікація, рішення прийняті.
**Попередній етап:** [spec.md](spec.md) · [interactions.md](interactions.md) — лишаються чинними для всього, що тут не перевизначено.
**Стиль:** [style-guide.md](style-guide.md) — без змін.

## 1. Що змінюється

| | Етап 1 | Етап 2 |
|---|---|---|
| Дані | IndexedDB, один локальний користувач | **MongoDB**, багато акаунтів |
| Картинки | Blob у браузері | **Cloudinary** |
| Вхід | немає | **імейл + пароль** |
| Ліміт бажань | немає | **30 на акаунт**, хардлок |
| Поділитися | текст + PNG | **посилання на живий список** + текст + PNG |
| Чужий список | неможливо | **гостьовий перегляд**, read-only |

Продуктова логіка етапу 1 — картки, «✓», видалення, фільтр, порожні стани, форма додавання, відмінювання лічильника — **не змінюється**. Нижче тільки дельта.

## 2. Модель даних

```
User {
  _id: ObjectId
  email: string            // unique, зберігається в нижньому регістрі
  passwordHash: string     // bcrypt
  name: string             // 3–15 символів
  shareToken: string       // unique, випадковий, ~10 символів
  createdAt: Date
}

Wish {
  _id: ObjectId
  userId: ObjectId         // індекс
  title: string            // до 60 символів
  emoji: string            // дефолт "🎁"
  imageUrl: string | null      // Cloudinary secure_url
  imagePublicId: string | null // потрібен, щоб видалити файл з Cloudinary
  price: number | null
  currency: "UAH" | "PLN" | "USD" | "EUR"
  url: string | null
  isDone: boolean
  createdAt: Date
}

Reservation {
  _id: ObjectId
  wishId: ObjectId         // яке бажання заброньоване
  listOwnerId: ObjectId    // userId власника списку — денормалізовано заради unique-індексу нижче
  guestId: string          // випадковий токен з cookie гостя, не пов'язаний з акаунтом
  guestName: string        // 1–30 символів, як ввів гість
  createdAt: Date
}
```

**Індекси:** `User.email` (unique), `User.shareToken` (unique), `Wish.userId`, `Reservation.wishId` (**unique** — одна бронь на бажання), `Reservation.(listOwnerId, guestId)` (**unique** — одна бронь на список від одного гостя). Другий індекс — не тільки оптимізація запиту, а й гарантія на рівні БД: подвійний клік або гонка запитів не створить дві броні від того самого гостя в одному списку.

**Що зникає:** `userId: "local-user"` — тепер це справжній `ObjectId`. Поле `Profile.email`, зарезервоване на етапі 1, стає робочим. Шар репозиторіїв із [tech-stack.md](tech-stack.md) отримує другу реалізацію — саме заради цього він і робився.

**`guestId` — не акаунт.** Це не `User._id` і не сесія. Гість, який бронює бажання, не реєструється: `guestId` — випадковий рядок у httpOnly-cookie браузера, який ідентифікує лише «цей пристрій», без імені, без пароля. Детально — розділ 5.4.

## 3. Автентифікація

**Механізм:** імейл + пароль.

- Пароль — **мінімум 8 символів**, хешується bcrypt (cost 12). У відкритому вигляді ніде не зберігається й не логується.
- Імейл нормалізується (`trim`, нижній регістр), унікальний.
- Сесія — Auth.js (NextAuth) з Credentials provider, JWT у httpOnly-cookie.
- Помилка входу завжди одна й та сама — «Невірний імейл або пароль», без уточнення, що саме не збіглося.

### 3.1. Екран реєстрації `/register`

Замінює Init-екран етапу 1.

Поля: **імʼя** (3–15, валідація як на Init) · **імейл** · **пароль** (мін. 8).
Кнопка «Створити акаунт» неактивна, поки всі три поля не валідні.

Після успіху: створюється `User` з випадковим `shareToken` → міграція локальних даних або 3 дефолтні картки (розділ 6) → перехід на «Мої бажання».

Помилки інлайн, Ember: «Такий імейл уже зареєстрований» · «Пароль мінімум 8 символів» · «Схоже, це не імейл».

### 3.2. Екран входу `/login`

Поля: імейл, пароль. Кнопка «Увійти». Посилання «Немає акаунта? Створити» → `/register`.

### 3.3. Вихід

Пункт у меню профілю на «Мої бажання» (там, де зараз клік по імені). Меню отримує два пункти: «Змінити імʼя» і «Вийти».

### 3.4. ⚠️ Відновлення пароля — свідома прогалина

**Скидання пароля неможливе без сервісу розсилки.** Ви обрали імейл+пароль, і в стеку немає нічого, що надсилає листи. Практичний наслідок: **забув пароль — втратив акаунт назавжди**, разом зі списком.

Для воркшопу це прийнятно. Якщо застосунок піде далі, потрібне одне з двох:

1. Підключити сервіс розсилки (Resend / Postmark — є безкоштовні тарифи) і зробити скидання за посиланням.
2. Додати вхід через Google як альтернативу — тоді пароль перестає бути єдиним ключем.

Поки що на екрані входу **не показуємо** посилання «Забули пароль?» — краще його відсутність, ніж кнопка, що нікуди не веде.

## 4. Ліміт 30 бажань

- Рахуються **всі** бажання акаунта — і активні, і здійснені. Обмеження диктує розмір безкоштовного кластера, а не продуктова логіка, тож «здійснені не рахуються» тут було б нелогічно.
- **Хардлок на сервері**, не тільки в UI: спроба створити 31-ше бажання відхиляється в Server Action. Клієнтська перевірка — зручність, серверна — гарантія.
- **UI:**
  - Поки бажань менше 25 — нічого не показуємо, лічильник звичайний.
  - Від 25 — у хедері поруч із лічильником зʼявляється муте-текст «28 / 30».
  - На 30 — кнопка «Додати» неактивна, поруч підпис «Ліміт 30 бажань. Видали щось, щоб додати нове».
  - Якщо якимось чином відкрито форму «Додати» при повному списку — кнопка збереження неактивна з тим самим поясненням.
- Видалення бажання одразу знімає блокування.

## 5. Поділитися і гостьовий перегляд

### 5.1. Посилання

- Кожен акаунт має `shareToken` — випадковий рядок ~10 символів, згенерований при реєстрації. Посилання виду `/w/8f3k2p9x`.
- Токен **непередбачуваний**: перебором чужі списки не знайти, і немає сторінки, що їх перелічує.
- Токен постійний, регенерації в цій ітерації немає (це наступний крок, якщо знадобиться «відкликати посилання»).

### 5.2. Екран «Поділитися» (свій, автентифікований)

До наявного (банер Amber, картки, «Зберегти як картинку») додається:

- **Поле з посиланням** і кнопка «Копіювати» — hairline-інпут у стані read-only, клік по кнопці копіює і на 2с змінює підпис на «Скопійовано ✓».
- Кнопка «Поділитися» (Web Share API) тепер передає **і текст, і URL**. Текст той самий, що на етапі 1, посилання додається окремим полем `url` — так месенджери зроблять клікабельне прев'ю.
- Фолбек на desktop — копіюється текст разом із посиланням.

### 5.3. Гостьовий екран `/w/{token}`

**Рендериться на сервері** — тут серверні компоненти нарешті дають реальну користь: сторінка відкривається швидко, працює без JS і має коректні OG-теги для прев'ю в месенджерах.

**Що бачить гість:**

- Банер Amber `#f59e0b`: «Список бажань {імʼя}» + лічильник.
- Картки: емодзі/картинка, назва, ціна, **посилання «Подивитися →»**.
- **Здійснені бажання не показуються** — як і на власному екрані «Поділитися».
- Жодних кнопок редагування: ні «✓», ні видалення, ні олівця. Картки некликабельні, крім посилання «Подивитися». **Єдина дія — бронювання** (розділ 5.4).
- Внизу — банер-CTA: «Створити свій список бажань» → `/register`. Ненавʼязливий, у стилі Neutral Card, без модалок і таймерів.

> **Відхилення від етапу 1.** У [spec.md 3.3](spec.md) екран «Поділитися» показував лише емодзі, назви й ціни — без посилань. Для гостьового перегляду посилання **додано навмисно**: саме воно робить фічу корисною — гість дивиться список, щоб щось купити, і без URL мусить шукати товар сам. Якщо це небажано — скажіть, приберемо.

**Стани:**

| Ситуація | Що показуємо |
|---|---|
| Токен не існує | Сторінка «Такого списку не існує» + кнопка «На головну» |
| Список порожній / усе здійснене | Банер + «Тут поки порожньо» + CTA реєстрації |
| Гість уже залогінений | Той самий read-only вигляд; CTA внизу замінюється на «Мій список» → `/` |
| Юзер відкрив **власне** посилання | Той самий вигляд + підказка «Так твій список бачать друзі» — **без жодних позначок бронювання** (див. 5.4) |

**Кнопки «Гість» немає.** Ви обрали показ списку одразу — окремий екран-шлюз із вибором «Увійти / Переглянути як гість» не потрібен: гість і так бачить контент без жодного кліку, а це і була мета. Роль «кнопки гостя» виконує CTA-банер унизу, який тепер працює в протилежний бік — не «пусти мене подивитись», а «зроби собі такий самий».

### 5.4. Бронювання бажань гостями

**Мета:** кілька людей дивляться той самий список і координуються, щоб не подарувати одне й те саме. Гість позначає одне бажання «своїм», інші гості це бачать, **власник — ні**.

#### Хто що бачить

| Хто дивиться | Що бачить |
|---|---|
| Інший гість (не бронював цей запис) | Бейдж «Заброньовано: Оксана» (Badge Soft), без дії |
| Гість, який сам забронював цей запис | Бейдж «Заброньовано тобою» (Badge Outline) + кнопка «Скасувати бронювання» |
| Той самий гість, дивлячись на **інші** бажання цього списку | Кнопки «Забронювати» на них **не показуються** — в одного гостя лише одна бронь на список |
| **Власник списку — завжди** | Нічого. Ні бейджа, ні лічильника «заброньовано N». Картка виглядає так само, як без жодної броні — і на «Мої бажання», і при перегляді власного `/w/{token}` |

Останній рядок — не деталь UI, а вимога до даних: ендпоінт, яким власник отримує **свої** бажання, не приєднує таблицю `Reservation` взагалі. Це не «приховати в інтерфейсі» — це «не покласти в відповідь». Приховане в UI, але присутнє в мережевій відповіді, видно за секунду в DevTools.

#### Ідентифікація гостя

- При **першій успішній броні** (не при відкритті сторінки) сервер видає cookie `guestId`: httpOnly, `sameSite=lax`, термін дії — 1 рік. До того, поки гість нічого не бронював, ідентифікувати нічим — і не треба.
- Оскільки cookie httpOnly, порівняння «це моя бронь чи чужа» рахується на сервері при рендері сторінки — сторінка й так серверна (5.3), тож зайвого клієнтського коду не додається.

> ⚠️ **Прийнятне обмеження.** `guestId` — це пристрій/браузер, не людина. Очищення cookie або інший пристрій дозволяють забронювати ще раз в тому самому списку. Це свідомо: фіча соціальна, «на чесність» (як реальне «я зайняв»), а не система захисту від зловживань. Вимагати акаунт заради одного кліка суперечило б усій логіці гостьового доступу.

#### Потік бронювання

1. Гість натискає «Забронювати» на вільному бажанні.
2. Інлайн, прямо на картці — той самий прийом, що для видалення на власному екрані (interactions.md 2.5): вміст картки доповнюється полем «Як тебе звати?» (1–30 символів, `trim`) і кнопкою «Підтвердити» (неактивна, поки поле порожнє). Кросфейд 150мс, без модалки.
3. Підтвердження → якщо `guestId` ще немає, сервер його видає; створюється `Reservation`. Картка одразу показує «Заброньовано тобою» + «Скасувати бронювання».
4. Кнопки «Забронювати» на решті карток цього списку зникають (гість уже має бронь тут).
5. **Скасування** — клік по «Скасувати бронювання» видаляє запис одразу, без підтвердження (симетрично до «✓» на власному екрані). Кнопки «Забронювати» повертаються на решту карток.
6. **Гонка запитів:** якщо двоє тиснуть «Підтвердити» на одне бажання одночасно, unique-індекс на `wishId` пропускає першого; другий отримує «Хтось інший щойно забронював це» і сторінка оновлює стан.

#### Крайні випадки

| Ситуація | Поведінка |
|---|---|
| Власник видаляє заброньоване бажання | `Reservation` видаляється каскадом разом із бажанням. Гість дізнається лише за наступного відвідування — картка просто зникла |
| Власник позначає заброньоване бажання здійсненим (`isDone → true`) | `Reservation` видаляється каскадом — здійснене й так зникає з гостьового екрана, лишати бронь без картки немає сенсу |
| Власник редагує назву/ціну/картинку заброньованого бажання | Бронь не чіпається, лишається на місці |

## 6. Міграція локальних даних

При першому вході (реєстрація або логін) клієнт перевіряє IndexedDB:

1. **Є локальні бажання** → одноразово заливаються в акаунт: картинки з Blob вивантажуються в Cloudinary, записи створюються з новим `userId`. Дефолтні 3 картки **не створюються**. Після успіху IndexedDB очищається.
2. **Локальних бажань немає** → створюються **3 дефолтні картки** (📚 Книжка про дизайн ₴450 · ✈️ Вихідні у Львові ₴3 000 · 🎧 Навушники ₴2 200, здійснене). Їх можна редагувати й видаляти як звичайні, і вони рахуються в ліміті 30.
3. **Локальних більше 30** → переносяться перші 30 за `createdAt`, решта відкидається з повідомленням «Перенесено 30 з N бажань — це максимум для акаунта».

Під час міграції — індикатор «Переносимо твої бажання…». Якщо міграція впала на середині, повторний вхід доливає те, чого бракує (ідемпотентність за локальним `id`, який зберігається у полі-мітці до завершення).

## 7. Картинки: Cloudinary

- Завантаження — **через сервер** (Server Action + підписаний запит), не напряму з браузера. Unsigned preset дозволив би будь-кому заливати файли у ваш акаунт.
- Обмеження ті самі: до 5 МБ, JPEG/PNG/WebP/GIF, клієнтське стиснення до ~1200px перед відправкою.
- Зберігаємо `secure_url` і `public_id`. **`public_id` обовʼязковий** — без нього видалене бажання лишить файл висіти в Cloudinary назавжди.
- Видалення бажання → видалення файлу з Cloudinary. Якщо запит на видалення файлу впав, бажання все одно видаляється (дані користувача важливіші за прибирання), помилка логується.
- Безкоштовний тариф — 25 кредитів/місяць; для воркшопу з запасом.

## 7-bis. Право власності на бажання

Редагування (див. [interactions.md 3-bis](interactions.md)) робить питання власності серверним, а не косметичним.

**Правило:** кожна мутація бажання — створення, редагування, «✓», видалення — перевіряє на сервері, що `wish.userId === session.user.id`. Перевірка в Server Action, не в компоненті.

- Приховати кнопку в UI **недостатньо**: Server Actions викликаються прямим HTTP-запитом, і зловмиснику не потрібна ваша кнопка.
- Чуже або неіснуюче бажання дають **однакову відповідь — 404**. Якщо чуже віддавати 403, а неіснуюче 404, різниця відповідей перетворюється на спосіб перевіряти, які `id` існують у базі.
- Перевірка живе в одному місці — хелпері на кшталт `requireOwnedWish(id, session)`, який або повертає документ, або кидає 404. Дублювати умову в кожному екшені означає рано чи пізно десь її забути.

**Гостьовий екран `/w/{token}` мутацій не має взагалі** — там немає ні кнопок, ні маршрутів редагування. Але серверна перевірка все одно обовʼязкова: гість, який знає структуру API, не має отримати запис у чужий список.

## 8. Що з етапу 1 лишається без змін

- Усі інтеракції списку: «✓» з переміщенням картки, інлайн-видалення, фільтр, три порожні стани, підсвічування нової картки.
- Форма «Додати»: поля, валідація, взаємовиключність емодзі й картинки, скасування з підтвердженням.
- Дизайн-система: палітра, радіуси 18/24, Ember тільки для деструктиву, Amber тільки для банера «Поділитися» і гостьового екрана.
- «Зберегти як картинку».
- Мобільна поведінка, клавіатура, `prefers-reduced-motion`.

## 9. Що свідомо не робимо

- Відновлення пароля (див. 3.4) · вхід через соцмережі.
- Регенерацію/відкликання посилання.
- Приватні списки, доступ за паролем, обмеження за списком людей.
- Коментарі, лайки, підписки на чужі списки.
- Rate limiting на створення броней — за межами цієї ітерації; технічно нічого не заважає гостю наштампувати брони під випадковими іменами на багатьох чужих списках. Для воркшопу ризик низький (потрібно знати чужі `shareToken`), але якщо застосунок стане публічним — варто повернутись.
- Регенерація/зняття броні власником напряму (власник її навіть не бачить, тож і знімати нема через що).
- Офлайн-режим: після переходу в хмару IndexedDB використовується лише для одноразової міграції.
