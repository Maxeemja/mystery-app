# Завдання для промптера — бронювання бажань гостями

**Тип:** інкремент поверх етапу 2. Потребує вже наявних `/w/{token}`, MongoDB, Server Actions.
**Джерела істини:** [stage-2.md 2](stage-2.md), [stage-2.md 5.4](stage-2.md) — повна поведінка · [stage-2.md 5.3](stage-2.md) — гостьовий екран, куди це вбудовується · [style-guide.md](style-guide.md) — стиль.

---

## 1. Що робимо і навіщо

Гість, який дивиться чужий список за посиланням `/w/{token}`, може позначити **одне** бажання своїм — щоб інші гості того самого списку бачили, що воно вже «зайняте», і не купили дублікат подарунка.

**Головне правило, яке визначає всю архітектуру: власник списку не бачить бронювання взагалі.** Не «прихована кнопка» — бекенд, що віддає власнику його ж бажання, не повинен містити дані про брони в цій відповіді жодним чином. Перевірка в DevTools мережевого запиту має нічого не показати.

**Бронювання без реєстрації.** Гість не створює акаунт — тільки вводить імʼя в момент бронювання. Ідентифікація — випадкова `guestId` cookie, видана лише тому, хто хоч раз забронював.

---

## 2. Модель даних

```
Reservation {
  _id: ObjectId
  wishId: ObjectId
  listOwnerId: ObjectId    // денормалізовано — для unique-індексу і швидких запитів
  guestId: string          // з cookie, не пов'язаний з User
  guestName: string        // 1–30 символів, trim
  createdAt: Date
}
```

**Індекси:** `unique(wishId)` — одна бронь на бажання; `unique(listOwnerId, guestId)` — одна бронь на список від одного гостя. Другий індекс — не оптимізація, а гарантія на рівні БД: без нього подвійний клік або гонка запитів може створити дві брони від того самого гостя.

**Каскади:**

- Видалення `Wish` → видалити повʼязаний `Reservation`.
- `Wish.isDone` стає `true` → видалити повʼязаний `Reservation` (здійснене й так зникає з гостьового екрана; лишати бронь без картки, яку ніхто не бачить, немає сенсу).

## 3. Ідентифікація гостя — `guestId`

- Cookie `guestId`: **httpOnly**, `sameSite=lax`, `path=/`, термін дії 1 рік.
- Видається **лише в момент першого успішного бронювання** — не при простому перегляді сторінки. До першої броні гостю нічого ідентифікувати, і зайва cookie нікому не потрібна.
- Оскільки cookie httpOnly, зіставлення «це моя бронь / чужа / вільно» рахується **на сервері** при рендері `/w/{token}` — сторінка вже серверна (stage-2.md 5.3), додаткового клієнтського стану для цього не треба.
- Немає звʼязку з `User`. Гість, який потім зареєструється, отримає новий, окремий `guestId` при наступному візиті як гість — міграції броні в акаунт немає, і не повинно бути в цій ітерації.

**Свідоме обмеження, не баг:** `guestId` ідентифікує пристрій/браузер, не людину. Очищення cookie чи інший браузер дозволяють забронювати повторно в тому самому списку. Фіча — соціальна, «на чесність», а не захист від зловживань; вимагати акаунт заради одного кліка суперечило б гостьовому доступу без реєстрації.

## 4. UI на картці `/w/{token}`

Три стани картки замінюють один. Порахувати стан **на сервері** при рендері, порівнюючи `Reservation.guestId` з cookie запиту:

| Стан | Вигляд |
|---|---|
| Вільне, у гостя немає броні в цьому списку | Кнопка «Забронювати» (Outline Button) |
| Заброньоване кимось іншим | Бейдж «Заброньовано: {guestName}» (Badge Soft — `#f5f5f5`/`#171717`), без кнопки |
| Заброньоване цим самим гостем | Бейдж «Заброньовано тобою» (Badge Outline), кнопка «Скасувати бронювання» |
| Вільне, але в гостя вже є бронь **десь у цьому списку** | Ніякої кнопки, ніякого бейджа — картка виглядає нейтрально |

Немає окремого стану «оберіть, а потім підтвердіть» через модалку — усе інлайн на картці.

### Потік

1. Клік «Забронювати» → **інлайн, на самій картці** (той самий прийом, що для видалення на власному екрані «Мої бажання» — content картки доповнюється, не відкривається модалка): поле «Як тебе звати?» (autofocus, `trim`, 1–30 символів) + кнопка «Підтвердити» (неактивна, поки поле порожнє). Кросфейд 150мс.
2. `Enter` у полі = клік «Підтвердити», якщо валідне.
3. Підтвердження → Server Action: якщо `guestId` cookie нема, видати нову; створити `Reservation`. Оптимістичний UI: картка одразу показує «Заброньовано тобою», кнопки «Забронювати» на решті карток списку зникають.
4. **Гонка запитів:** якщо унікальний індекс `wishId` відхиляє вставку (хтось встиг першим) — показати «Хтось інший щойно забронював це» і оновити стан картки з сервера.
5. «Скасувати бронювання» → видалення `Reservation` **без підтвердження** (симетрично до «✓» на власному екрані — легка, оборотна дія). Кнопки «Забронювати» повертаються на решту карток.

### Стиль

- Кольору поза системою **не додається**. Badge Soft і Badge Outline — уже наявні компоненти з [style-guide.md](style-guide.md), нового токена не треба.
- «Забронювати» і «Скасувати бронювання» — Outline Button, той самий розмір і вага; на цьому екрані головний CTA — «Створити свій список» унизу, кнопки бронювання не повинні з ним конкурувати.

## 5. Захист даних власника — критична вимога

Це не тонкощ UI, а вимога до архітектури запитів:

- Функція/запит, яким **власник** отримує свої бажання (для «Мої бажання», для власного перегляду `/w/{token}`), **не приєднує** `Reservation` взагалі — ні в яких полях, ні прихованих, ні для внутрішньої логіки, що потім фільтрується на клієнті.
- Функція, яка збирає дані для **гостя**, — окрема, зі своїм джойном `Reservation`.
- Якщо в кодовій базі одна спільна функція будує список бажань і для власника, і для гостя (спокуслива оптимізація) — **не варто**: один параметр забутий за кілька місяців, і власник побачить бронювання в мережевій відповіді.
- Це підтверджується так само, як [stage-2.md 7-bis](stage-2.md) вимагає для власності: приховати кнопку недостатньо, потрібна перевірка на рівні даних, а не рендеру.

---

## 6. Що не чіпати

- Усе з `/w/{token}`, крім самих карток: банер Amber, CTA реєстрації, стани «токен не існує» / «порожньо».
- «Мої бажання», «Додати», «Редагувати», «Поділитися» (свій) — жодних змін. Власник цієї фічі не бачить ніде.
- Право власності на мутації бажання (stage-2.md 7-bis) — бронювання додає паралельну, окрему перевірку прав, а не замінює наявну.
- Ліміт 30 бажань — брони не рахуються в ньому, це не бажання, а окрема колекція.

---

## 7. Чек-лист приймання

- [ ] Вільне бажання показує «Забронювати»; клік розкриває інлайн-поле імені на картці, без модалки
- [ ] «Підтвердити» неактивна, поки імʼя порожнє; `Enter` підтверджує
- [ ] Після броні картка показує «Заброньовано тобою» + «Скасувати», інші картки списку ховають «Забронювати»
- [ ] Інший гість (інший браузер / очищені cookie) бачить те саме бажання як «Заброньовано: {імʼя}», без кнопки
- [ ] «Скасувати бронювання» видаляє бронь без підтвердження, кнопки «Забронювати» повертаються
- [ ] Одночасна спроба двох гостей забронювати те саме — другий отримує повідомлення, дублю в базі немає
- [ ] **Власник на «Мої бажання» і на власному `/w/{token}` не бачить жодних слідів бронювання — перевірено і в UI, і в мережевій відповіді (DevTools)**
- [ ] Видалення бажання власником прибирає і його бронь
- [ ] Позначення бажання здійсненим власником прибирає його бронь
- [ ] Редагування назви/ціни/картинки заброньованого бажання не чіпає бронь
- [ ] `guestId` cookie не зʼявляється до першої броні; httpOnly, не читається з JS
- [ ] Ліміт 30 бажань і право власності на редагування/видалення працюють як раніше, не зламані цією фічею
