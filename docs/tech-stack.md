## 2. Чому IndexedDB, а не localStorage

Не косметичний вибір — його диктує вимога з [spec.md](spec.md): картинка бажання **до 5 МБ**.

- localStorage зберігає **тільки рядки**. Картинку довелось би тримати в base64, а це +33% обсягу.
- Загальна квота localStorage — **5–10 МБ на весь домен**. Одна картинка на 5 МБ (≈6.7 МБ у base64) вичерпує її повністю.
- localStorage **синхронний** — читання/запис блокують головний потік.

IndexedDB зберігає `Blob` нативно, має квоту в сотні мегабайт і працює асинхронно. Для профілю (одне коротке імʼя) різниці немає, але тримати обидва сховища немає сенсу — усе в IndexedDB.

Клієнтське стиснення картинки до ~1200px перед записом лишається обовʼязковим — воно з [interactions.md 3.3](interactions.md) і не скасовується.

## 3. Головне тертя: Server Components і локальне сховище

**Проблема.** Server Components виконуються на сервері й **не мають доступу до IndexedDB** — це browser-only API. На етапі 1 усі дані лежать у браузері, отже кожен компонент, що читає або пише бажання, мусить бути клієнтським (`'use client'`).

**Наслідок.** На етапі 1 RSC не дає майже нічого: застосунок фактично працює як SPA всередині Next.js. Реальну вигоду серверні компоненти принесуть на етапі 2, коли зʼявиться MongoDB.

**Це прийнятно і не потребує зміни рішення** — Next.js береться саме як заділ під етап 2. Але варто розуміти, що на етапі 1 це «Next.js без половини Next.js», а не оптимальний вибір для локального прототипу самого по собі.

**Що з цього випливає практично:**

- Серверними лишаються тільки статичні частини: layout, оболонка сторінки, елементи без даних.
- Усе, що торкається бажань і профілю, — клієнтське.
- **Гідратація.** Сервер відрендерить порожній список (даних у нього немає), клієнт після монтування отримає реальні. Без обробки це дасть hydration mismatch і блимання. Рішення: до завершення читання з IndexedDB рендерити скелетон, а не порожній стан — інакше користувач на частку секунди побачить «Поки що жодного бажання» при непорожньому списку.
- **Init-екран** з тієї ж причини не можна вирішувати серверним редиректом — наявність профілю відома лише клієнту.

## 4. Шар доступу до даних

Ключова вимога з [spec.md](spec.md) і [prompter-task.md](prompter-task.md): перехід на етап 2 має бути **перенесенням даних, а не переписуванням**.

Тому весь доступ до даних іде через один інтерфейс — репозиторій:

```ts
interface WishRepository {
  list(userId: string): Promise<Wish[]>
  create(userId: string, data: NewWish): Promise<Wish>
  update(id: string, patch: Partial<Wish>): Promise<Wish>
  remove(id: string): Promise<void>
}

interface ProfileRepository {
  get(userId: string): Promise<Profile | null>
  save(profile: Profile): Promise<Profile>
}
```

- **Етап 1:** реалізація `IndexedDbWishRepository`, `userId` завжди `"local-user"`.
- **Етап 2:** реалізація `MongoWishRepository`, викликається через Server Actions; `userId` — реальний.

Компоненти **не звертаються до IndexedDB напряму** й нічого не знають про сховище. `userId` передається завжди, навіть коли значення одне — інакше на етапі 2 доведеться правити кожен виклик.

## 5. Структура

```
app/
  layout.tsx              server
  page.tsx                «Мої бажання» — оболонка server, вміст client
  add/page.tsx            «Додати»
  share/page.tsx          «Поділитися»
  init/page.tsx           Init
components/               client-компоненти (картки, форма, модалки, банер)
lib/
  db/                     IndexedDB: схема, відкриття, міграції
  repositories/           WishRepository, ProfileRepository + реалізації
  domain/                 типи Wish, Profile; правила (валідація, відмінювання, форматування ціни)
  share/                  Web Share + фолбек, генерація PNG
styles/                   токени дизайн-системи
```

`lib/domain/` не залежить ні від React, ні від сховища — там чиста логіка (валідація імені 3–15, українське відмінювання лічильника, форматування `₴3 000`, транслітерація імені файлу). Ця частина переживе етап 2 без єдиної правки.

## 6. Специфічні до стека вимоги

- **Web Share API** — `navigator.share` є не всюди; фолбек на `navigator.clipboard.writeText` обовʼязковий ([interactions.md 4.2](interactions.md)).
- **Рендер PNG** — DOM у зображення на клієнті (`html-to-image` або аналог). Емодзі мають потрапити в PNG коректно — це найризикованіше місце, залежить від системних шрифтів; перевірити на macOS і Android окремо.
- **`prefers-reduced-motion`** — обробляти на рівні CSS, не в JS.
- **Тестові дані** засіваються при першому відкритті, якщо база порожня, і **тільки разом зі створенням профілю** — щоб не зʼявитись повторно після того, як користувач видалив усі бажання вручну.

## 7. Що врахувати перед етапом 2

Не блокує роботу зараз, але вплине на рішення пізніше:

1. **MongoDB проти корпоративного дефолту.** Загальний стек компанії — PostgreSQL. Модель даних тут проста, плоска й реляційна за природою (user → wishes), тобто аргументів саме за документну БД небагато. Для воркшопу вибір нормальний; якщо проєкт піде далі — варто свідомо підтвердити, а не успадкувати за інерцією.
2. **Авторизація «імʼя + імейл»** без пароля — це або магічні посилання, або взагалі не автентифікація, а ідентифікація. Різниця суттєва для приватності: списки бажань стануть доступні за знанням імейла.
3. **Міграція локальних даних.** Коли зʼявиться акаунт, бажання з `userId = "local-user"` треба одноразово перепривʼязати до реального користувача — інакше вони «зникнуть» після першого логіну.
